# ADR-0011: Pre-1.0 Versioning, and the Two Surfaces That Get a Deprecation Path

- **Status**: Accepted
- **Date**: 2026-08-24
- **Resolves**: `TODO(PRE_1_0_VERSIONING)`, open since the constitution's ratification
- **Principles engaged**: VIII (Reproducibility and versioning), XII (Open-source quality)

## Context

Principle XII says the project "follows semantic versioning". Semantic versioning says nothing
useful about `0.x`: by its own text, anything may change at any time before `1.0.0`, which is a
policy in the sense that "no rules" is a policy. Meanwhile the kernel API is expected to churn —
Milestone 7 alone changed `SpanIndex` and added a model validator to `Document`.

So the two halves are in tension, and the constitution has carried the tension as an open decision
since the founding, gated on "before first public release". This is the last milestone with a plan
capable of carrying it. A decision that outlives the last plan able to make it does not get made
later; it gets made accidentally, by the first release that ships without one.

## Decision

### 1. While the major version is `0`

| Bump | Promise |
|---|---|
| **minor** (`0.4.0` → `0.5.0`) | May break any public API. |
| **patch** (`0.4.1` → `0.4.2`) | Never breaks a public API. |

Every breaking change ships with a `CHANGELOG.md` entry naming **what moved and what to do about
it**. A breaking change with no entry is a defect, not a release note somebody forgot.

That is the whole promise for the Python API, and it is deliberately narrow. A broader claim —
"the kernel is stable", "`Document` will not change" — would be broken inside one release, and a
stability promise nobody keeps is worse than none: it is the reason a downstream project pins to a
version and stops upgrading.

### 2. Two surfaces get a deprecation path instead of a silent break

**The kernel's identity derivations** — `blob_id`, `document_id`, and the artifact chain of
ADR-0003 — and **the on-disk artifact format** of ADR-0010.

A change to either invalidates data that already exists on somebody else's disk. Everything else in
this project can be fixed by upgrading and re-running; these cannot, because the thing they break is
not code. A stored artifact whose identity derivation moved is unreachable, and a stored artifact
whose format moved is unreadable — and in both cases the owner finds out when a cache silently stops
hitting, which is the least legible failure this system has.

So a change to either MUST:

1. ship in a minor bump, never a patch;
2. move the version that exists for it — `IDENTITY_SCHEMA_VERSION` in the kernel, or the relevant
   `artifact_format_version` — so the mismatch is *detected* rather than inferred;
3. state in the changelog what becomes unreachable and whether clearing the store is required.

Note the second clause is already load-bearing rather than aspirational: `FileArtifactStore.get`
treats an incompatible `artifact_format_version` as a **miss that is logged**, so an artifact written
under an older format is recomputed rather than misread. The deprecation path is therefore not a
promise about future care; it is a mechanism that already runs.

### 3. Nothing else is promised stable before `1.0.0`

Not the CLI's flags, not the HTTP paths, not the schema-file format, not the error messages. The
exit codes and the HTTP status mapping are documented contracts and will be treated as such in
practice, but they are not covered by this ADR, and a caller pinning to them before `1.0.0` should
pin a version.

## Consequences

- **The constitution's open-decision table is empty.** This was the last item on it, and every
  entry now points at an accepted ADR (SC-016).
- **`0.x` minor bumps are the release unit for anything interesting.** In practice most releases in
  this line will be minor, which is the honest shape for a pre-1.0 project rather than a
  patch-version fiction.
- **The two protected surfaces are the two that already carry versions.** That is not a coincidence
  and is the reason those versions exist: ADR-0002 and ADR-0010 both introduced one precisely
  because the data outlives the code that wrote it.
- **`1.0.0` is not scheduled by this ADR.** What it would mean — which surfaces become stable, and
  on what evidence — is a decision for whoever proposes it, with this document as the statement of
  what was true before.

## Alternatives considered

**Leave it open.** The constitution permits it: the gate is "before first public release", not this
milestone. Rejected for the reason in Context — the decision would then be made by the first release
that shipped without it, silently and by nobody in particular.

**Promise the kernel stable now.** It is the most-depended-on surface and the one a downstream
project would most like pinned. Rejected as false: the kernel changed in this milestone and will
change again, and a promise contradicted by the next release teaches readers to disbelieve the
others.

**Protect every stored surface, including prediction sets and golden-set files.** Attractive, and
too broad to keep. A prediction set is regenerable from its inputs by design — that is what
`make_dataset.py` is — so it does not have the property that makes the other two special.
